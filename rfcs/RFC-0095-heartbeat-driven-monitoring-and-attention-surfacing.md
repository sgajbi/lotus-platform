# RFC-0095: Heartbeat-Driven Monitoring And Attention Surfacing

- Status: Draft
- Date: 2026-04-21
- Owners:
  - lotus-platform governance
  - lotus-ai runtime owners
  - affected domain-service owners for surfaced conditions
- Target repositories:
  - `lotus-platform`
  - `lotus-ai`
  - optionally `lotus-manage` after first-wave platform and AI proof
- Depends on:
  - `RFC-0093-lotus-context-assembly-and-compaction-hardening-for-agentic-development.md`
  - `RFC-0094-durable-background-engineering-task-ledger-and-governed-delegation-model.md`
  - `lotus-ai` RFC-0031, RFC-0032, and RFC-0033 bounded workflow-pack implementation

## Summary

Lotus needs a governed heartbeat plane that periodically surfaces operational attention items without
requiring agents, reviewers, or operators to manually poll every repository, GitHub PR, workflow-pack
run ledger, supportability surface, and certification artifact.

This RFC introduces a heartbeat-driven monitoring model for platform and AI engineering operations.
The heartbeat does not become a new source of truth. It reads governed sources, records evidence,
classifies attention posture, and produces bounded notifications or work items.

## Problem

The platform now has several durable truth sources:

1. GitHub Actions and PRs for check status,
2. RFC-0094 background-run ledger artifacts for local automation,
3. lotus-ai workflow-pack run ledgers and review-state surfaces,
4. mesh certification and operating reports,
5. platform context and AGENTS synchronization checks,
6. GitHub wiki publication posture.

These surfaces are useful, but they still require deliberate polling. Long-running work can drift
when stale reviews, failed checks, degraded AI runs, unpublished wiki changes, or stale context
updates are not surfaced quickly.

## Goals

1. Define a heartbeat model for periodic, governed attention surfacing.
2. Preserve source-of-truth ownership for each monitored surface.
3. Standardize attention item identity, severity, owner, evidence refs, and recommended next action.
4. Make heartbeat runs auditable through RFC-0094 task-ledger semantics.
5. Provide first-wave checks for:
   - stale GitHub PR checks,
   - unresolved or long-pending PRs,
   - degraded or failed workflow-pack runs,
   - stale review-state items,
   - degraded supportability summaries,
   - stale mesh certification or operating-report evidence,
   - unpublished wiki drift,
   - AGENTS/context synchronization drift.
6. Avoid noisy alerting by making deduplication and suppression explicit.

## Non-Goals

1. Replacing GitHub Actions, PR state, or runtime status APIs as source of truth.
2. Building a general incident-management system.
3. Creating banker-facing alerting before the engineering/operator heartbeat is proven.
4. Adding unrestricted background daemons in application services.
5. Turning every warning into a blocking issue.

## Current Reality

Part of the foundation already exists:

| Surface | Current state |
| --- | --- |
| GitHub PR and check status | Available through `gh`, GitHub Actions, and existing PR monitor scripts |
| Local background runs | Governed by RFC-0094 ledger semantics |
| Agent context preservation | Governed by RFC-0093 |
| Workflow-pack run and review posture | Implemented for bounded Phase-1 in `lotus-ai`, `lotus-gateway`, and `lotus-workbench` |
| Mesh certification posture | Generated by existing platform certification automation |
| Wiki publication posture | Governed by `automation/Sync-RepoWikis.ps1` |

The missing layer is a scheduled, deduplicated, evidence-bearing heartbeat that ties these surfaces
into one operator attention model.

## Proposed Model

### Heartbeat Run

Each heartbeat run is a governed background engineering task:

1. `task_kind`: `VALIDATION_RUN` or a future `HEARTBEAT_MONITOR`
2. durable `engineering_task_id`,
3. owner,
4. source refs,
5. started and ended timestamps,
6. evidence artifacts,
7. terminal status.

If this RFC needs a new task kind, it must extend
`platform-contracts/agent-engineering/engineering-task-ledger-contract.v1.json` with tests.

### Attention Item

Each item must carry:

1. stable `attention_item_id`,
2. `source_system`,
3. `source_ref`,
4. `repository`,
5. optional `pr_number`,
6. optional `workflow_pack_id`,
7. optional `run_id`,
8. severity: `info`, `warning`, `action_required`, `blocking`,
9. owner,
10. first seen and last seen timestamps,
11. evidence refs,
12. recommended next action,
13. suppression or deduplication key.

### Source Ownership

Heartbeat output may summarize and route; it must not redefine source truth.

| Source | Truth owner | Heartbeat behavior |
| --- | --- | --- |
| GitHub check status | GitHub Actions | read and classify |
| PR state | GitHub | read and classify |
| local background runs | RFC-0094 artifacts | read and classify |
| workflow-pack run posture | `lotus-ai` | read via governed API or artifact |
| Workbench review display | `lotus-workbench` through gateway | probe only when UI validation is explicitly requested |
| mesh certification | platform generated artifacts | read and classify |
| wiki publication | repo `wiki/` and `*.wiki.git` remote | run check and classify |

## Implementation Plan

### Slice 1: Heartbeat Contract And Attention Schema

1. Add a platform contract for heartbeat runs and attention items.
2. Define severity, source-system, evidence-ref, owner, and suppression fields.
3. Add validator and unit tests.

Review gate:

1. confirm the schema does not duplicate RFC-0094 task-ledger fields,
2. confirm source-of-truth language is explicit,
3. confirm attention IDs preserve operational identifiers.

### Slice 2: Platform Heartbeat Runner

1. Add `automation/Run-Heartbeat.ps1` or equivalent repo-native runner.
2. Read configured checks from platform-owned configuration.
3. Emit JSON and Markdown evidence.
4. Record RFC-0094-compatible task-ledger metadata.

Review gate:

1. confirm deterministic output paths,
2. remove duplicate check logic when existing scripts can be called,
3. test degraded and empty-state output.

### Slice 3: First-Wave Source Checks

Implement first-wave checks for:

1. stale PR checks,
2. stalled or failed background runs,
3. unpublished wiki drift,
4. AGENTS/context synchronization drift,
5. stale mesh operating evidence.

Review gate:

1. ensure each check reads the strongest available evidence,
2. ensure no check silently treats missing evidence as success,
3. add focused tests for stale, missing, and healthy cases.

### Slice 4: Workflow-Pack Attention Inputs

Add bounded workflow-pack checks for:

1. failed or degraded run ledger posture,
2. stale `awaiting_review` items,
3. superseded or expired runs that still appear active,
4. supportability surfaces that require operator attention.

Target repos:

1. `lotus-ai` owns source posture,
2. `lotus-gateway` may expose summary posture if needed,
3. `lotus-workbench` remains a consumer, not heartbeat truth.

Review gate:

1. verify runtime state and review state remain separate,
2. verify gateway/workbench are not treated as source of ledger truth,
3. add contract tests against representative run/review states.

### Slice 5: Operator Output And Deduplication

1. Produce a stable attention report.
2. Deduplicate repeated items by source ref and condition.
3. Preserve first-seen and last-seen posture where evidence exists.
4. Define suppression rules for accepted temporary conditions.

Review gate:

1. test repeat-run behavior,
2. confirm suppressions are explicit and auditable,
3. confirm no noisy one-off output becomes blocking by default.

### Slice 6: Code Review, API Certification, And Governance Tightening

Second-last mandatory slice.

1. Review all heartbeat code for duplicated polling logic.
2. Confirm contracts follow the API certification pattern where machine-readable APIs or artifacts
   are introduced.
3. Confirm OpenAPI/vocabulary impact is either tested or explicitly not applicable.
4. Confirm task-ledger and context-preservation rules are still aligned with RFC-0093/RFC-0094.
5. Remove dead or stale monitoring paths discovered during implementation.

### Slice 7: Documentation, Context, Wiki, Skills, And Branch Hygiene

Final mandatory slice.

1. Update runbooks and automation docs.
2. Update central agent context if heartbeat operation becomes platform-wide agent guidance.
3. Update repo-local wiki source if operator-facing behavior changes.
4. Assess whether `platform-automation-ops` or a new skill needs heartbeat guidance.
5. Run `Sync-RepoWikis.ps1 -CheckOnly` before merge and publish after merge if wiki changed.
6. Record final validation evidence, PR checks, and branch cleanup.

## Acceptance Criteria

1. Heartbeat output has a stable contract and validator.
2. First-wave checks produce healthy, warning, and action-required examples in tests.
3. Missing evidence is classified truthfully.
4. Attention items preserve repo, branch, PR, check, run, and artifact identifiers exactly.
5. Workflow-pack review/run posture is consumed without collapsing runtime state and review state.
6. The heartbeat runner can be executed locally and in GitHub-backed automation.
7. Final docs, context, wiki, skills, and branch hygiene are complete.

## Initial Priority

Implement first. This RFC should precede governed multi-agent delegation and task-flow runtime
because those later efforts create more long-running work that needs heartbeat visibility.
